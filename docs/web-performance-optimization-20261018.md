## 优先优化的原因与改法

### 全屏 Bloom 重复计算完整合成

**优先级 P0，GPU 方向的首要候选。**

[后处理 shader](C:/Projects/ShakeHero/assets/Shaders/BLGL/LayeredCinematic.shader:24) 的一次 `composed()` 读取 UI、场景、浮尘、光纹4张纹理，并计算受光增益。通用 Bloom 有3个尺度，每个尺度9次 `bright()`，每次又重新执行 `composed()`。

按源码展开，通用 Bloom 对每个适用像素执行27次合成、108次纹理采样调用；加上原始合成、方向标记与噪点，共约115次。摇晃时，灯带邻域的9×9双尺度循环还会额外展开325次纹理采样调用。后者仅限灯带附近，并非整屏。编译器可能复用部分结果，这些数字不是 GPU 实际指令或采样计数。

**改造方式：**先合成一次受光后的颜色，再从该颜色提取高光；在半分辨率或四分之一分辨率纹理中做横向、纵向可分离模糊，最后上采样合成。灯带保留实际点亮颜色和遮罩，使用小范围低分辨率模糊，替换当前逐像素大卷积。暗角和扫描纹继续保留。

**先做对照：**在同一存档、同一分辨率下关闭“泛光”，分别记录三选一与摇晃。此开关同时去掉通用和灯带 Bloom；若要区分两者，再增加独立诊断开关。现有 `enabled=false` 仍会执行基础合成和 RTT，不能视作绕过整条后处理管线，见 [Post 参数与提交](C:/Projects/ShakeHero/scripts/Machine/CinematicPost.lua:66)。

### 页面同步反复写入相同样式

**优先级 P0，CPU 与布局方向的首要候选。**

[View.Update](C:/Projects/ShakeHero/scripts/Bottle/View.lua:1052) 先调用机台更新，后者末尾同步页面；`View.Update` 末尾又同步一次。[每次 SyncPages](C:/Projects/ShakeHero/scripts/Machine/LayeredSkin.lua:576) 内部还调用两次 `pageMotion:Targets()`。加上独立的 [PageMotion.Tick](C:/Projects/ShakeHero/scripts/Machine/PageMotion.lua:167)，常规一帧可形成约5轮 `Apply()`。

[Apply](C:/Projects/ShakeHero/scripts/Machine/PageMotion.lua:122) 每次对同一入口写入裁剪、位置、变换与交互样式，即使弹簧已经停稳。参考 UI 库的 [SetStyle](C:/Projects/ShakeHero/urhox-libs/UI/Core/Widget.lua:1735) 每次都会应用 Yoga 样式并标记布局更新。这证明存在重复样式提交，不能直接等同于每帧发生5次完整布局计算。

**改造方式：**页面状态改变时统一同步一次，去除重复 `Targets()`；缓存阶段、页面开关、可见性和缩放状态。弹簧停稳且交互状态不变时停止 `Apply()`；仅变换改变时提交变换，仅布局改变时提交布局。[FitNumbers](C:/Projects/ShakeHero/scripts/Machine/LayeredSkin.lua:612) 改为目标值或缩放变化时更新。

不要把所有 `SetText()` 都列为布局问题：当前 Label 和 Button 已有文本相同即返回的判断。应先消除没有变化检查的 `SetStyle()` 路径。

**验收重点：**三选一进退场、候选选择、快速反向打开、悬停、点击区域和旧按下状态失效行为均保持正确。

### 像素精灵在离屏 UI 中逐矩形提交

**优先级 P0，CPU 与绘制提交方向的首要候选。**

[Post.Resize](C:/Projects/ShakeHero/scripts/Machine/CinematicPost.lua:54) 将 UI 绑定到离屏纹理，并注册为 offscreen context。[DrawSprite](C:/Projects/ShakeHero/scripts/Bottle/Art.lua:114) 因而对每条同色像素短矩形分别调用 `nvgBeginPath`、`nvgRect`、`Fill`。物品图标、遗物、候选和瓶内物品都可能经过这一路径。

复用实际精灵工厂计数后，开始页16种候选图形每件有36至105个矩形，平均63.06个。若22个下落道具都参与绘制，均匀抽样时仅道具就约有1387次 `Fill` 提交／帧。这个例子说明提交规模；三选一与瓶内的实际数量应现场计数，`Fill` 次数也不等于最终 GPU draw call 数。

**改造方式：**将现有像素行与色板确定性烘焙为图集，运行时每个普通图标绘制一个带 UV 的矩形。保留最近邻、透明边缘、镜像、旋转、原色和冷却灰阶；灰阶可预烘第二份图集，不能用乘灰色冒充去饱和。培根软体仍按分段 UV 绘制。缓存图像句柄，禁止逐帧创建纹理。

当前逐矩形分支用于兼容离屏 stencil，不能直接删除兼容分支、恢复复合路径来“合批”。改造后需比对原像素输出与透明区域。

### 多张渲染目标随物理分辨率增长

**优先级 P1，与 Bloom 改造一并处理。**

当前有5张全屏 RGBA 目标：UI capture、后效 output、场景合成层、浮尘合成层、灯面 mask。另有812×1756的机台源 RTT 和804×1748的浮尘源 RTT，见 [Post](C:/Projects/ShakeHero/scripts/Machine/CinematicPost.lua:40)、[SceneLayers](C:/Projects/ShakeHero/scripts/Machine/SceneLayers.lua:19)、[灯面 mask](C:/Projects/ShakeHero/scripts/Machine/LampBloomMask.lua:13)、[源 RTT](C:/Projects/ShakeHero/scripts/Machine/LitSpriteScene.lua:61)。

仅按上述颜色目标估算：

| 实际渲染物理尺寸 | 颜色目标合计 |
|---|---:|
| 402×874 | 17.50 MiB |
| 804×1748 | 37.61 MiB |
| 1080×1920 | 50.35 MiB |
| 1206×2622 | 71.11 MiB |

估算为 `5 × W × H × 4 + 两张固定源 RTT`，未包含深度、阴影、后端中间缓冲、素材和背缓冲。只有浏览器实际 canvas 随 DPR 扩大时才适用相应尺寸，必须读取运行值。

**改造方式：**文字与交互 UI 保持清晰，优先降低 Bloom、浮尘和灯面 mask 的分辨率；再评估场景中间层是否能直接采样固定源 RTT，减少全屏复制。设置独立的表现质量档位，避免高 DPR 自动放大全部特效成本。

RTT 尺寸变化继续在渲染前准备，保持402×874设计坐标、安全区、输入逆变换和方向契约。不同尺寸纹理应分别使用自己的 texel size，尤其要同步修正 mask 的方向标记采样，不能只替换 `SetSize()` 的宽高。

### 浮尘每帧重算噪声并重建网格

**优先级 P1，两个场景共同开销。**

[DustField](C:/Projects/ShakeHero/scripts/Machine/DustField.lua:32) 固定创建500个粒子。每帧遍历全部粒子，对其中移动粒子每个计算4次噪声；可见粒子逐个提交六顶点及法线、颜色、UV，最后 `Commit()`。这会产生 Lua 运算、临时对象和引擎绑定调用。

**改造方式：**先复用现有浮尘开关验证影响；低档减少数量，例如100至150个，并以20至30Hz更新模拟，显示时插值。提前缓存固定数据与 UV，避免循环内重复构造六顶点模板。若采样仍显示明显开销，再考虑引擎支持的粒子或批量更新方案。数量、频率为待验证参数。

背景机台另有实时阴影与九宫格独立几何，作为后续对照项：先测阴影关闭、静态层缓存和减少独立提交的收益，再决定改造范围。

### 物理补算会放大摇晃阶段的长帧

**优先级 P1，仅针对摇晃。**

[主循环](C:/Projects/ShakeHero/scripts/main.lua:329) 将全部 `dt` 加入累积器，然后按1/60秒连续补算，没有每帧步数预算。一次200ms长帧，在阶段未变化且剩余时间足够时会尝试补约12步；每一步还执行接触快照、规则、事件和完整物理同步。

[BottleItems](C:/Projects/ShakeHero/scripts/Bottle/Game.lua:358) 每次重新构造并排序列表；[Contacts](C:/Projects/ShakeHero/scripts/Bottle/Physics.lua:852) 每步构造接触数据；[Physics.Sync](C:/Projects/ShakeHero/scripts/Bottle/Physics.lua:665) 再建立成员表并排序。这些可形成临时分配与 GC 压力。

**改造方式：**先记录每帧补算步数、累积欠账、各段耗时与 GC。设置每帧补算预算并跨帧摊还，切后台恢复单独处理；同步改为成员、定义或体积变化时的差量更新。成员列表按成员版本失效缓存，不能只缓存 uid 而忽略转化、生成、移除与缩放事件。

固定步长、接触排序和玩法随机序列继续保留。不能直接丢掉累积时间或降低规则频率，否则会改变10秒摇晃、冷却、触发与结算语义。持续负载超过预算时，优先降低表现开销。

## 启动加载专项

这部分影响首次进入与首用停顿，不能单独解释三选一持续掉帧。

当前 [资源配置](C:/Projects/ShakeHero/.project/resources.json:4) 将 `audio/**` 整组预下载。音频源文件合计32.89 MiB，其中 [SynthStuff.wav](C:/Projects/ShakeHero/assets/audio/SynthStuff.wav) 占27.34 MiB，162.49秒、44.1kHz、双声道16位 PCM，并由 [Music.Init](C:/Projects/ShakeHero/scripts/Bottle/Audio.lua:81) 加载。

建议先把长 BGM 转为项目已支持的压缩音频，保留原节拍与循环点。以128至160kbps估算，162.49秒编码数据约2.48至3.10 MiB；实际文件、音质与构建后传输量需验证，压缩文件也不代表解码内存同比减少。

预下载曾用于修复音频占位长度导致的提前停止，应先压缩，再缩小为实际使用的启动音频组，保留资源就绪与时长校验。不要直接清空全部音频预下载。

此外，[Start](C:/Projects/ShakeHero/scripts/main.lua:190) 无条件加载并执行完整规则测试，应迁移到开发验证入口，生产保留必要的轻量配置检查。当前 `groups.default=["**"]` 为全量引用；确认动态资源引用和构建 manifest 后，才考虑裁剪旧资源与测试模块。全量入包不代表全部资源都在首屏下载或常驻内存。

音效已有固定池和碰撞节流，不优先归因为“碰撞时无限创建声源”。PNG源文件合计约1.94 MiB，也不应先把精力放在泛泛压缩所有图片上。

## 实施顺序与工作量

以下为初步工程估算，按顺序交付小批改动；每批测完再决定下一批，避免同时修改后失去归因。

| 顺序 | 工作 | 交付与判断条件 | 估算 |
|---|---|---|---|
| 1 | 建立浏览器基线与开关对照 | 三选一／摇晃的逐帧分布、开关差值、CPU或GPU方向判断 | 0.5天 |
| 2 | 去重页面同步，停稳后停止样式写入 | 样式提交计数显著下降；选择和点击回归通过 | 0.5至1天 |
| 3 | Bloom先合成后低分辨率模糊 | 消除重复完整合成与灯带大卷积；对比帧时间和灯效 | 1至2天 |
| 4 | 像素图集与浮尘优化 | 图标提交数量下降；原色、冷却、软体、透明度通过比对 | 1至2天 |
| 5 | 摇晃补算预算与差量物理同步 | 无补算尖峰放大；确定性规则与真实接触回归通过 | 1至2天 |
| 并行准备 | BGM压缩及启动自检拆分 | 冷启动改善，音乐无提前结束或循环接缝 | 0.5至1天 |

初步合计约4.5至8.5个工作日；实际范围由第一步采样决定，可在前两批达到目标后停止扩大改造。BGM材料准备可与渲染工作穿插进行。

## 验证与验收

### 固定场景记录

记录设备、浏览器、渲染后端、实际 canvas物理尺寸、DPR、代码版本、质量档和存档。每组至少跑3次，区分首次运行、资源和 shader 已预热后的稳定运行。

- 三选一：弹簧停稳后保持30秒，再连续切换候选及详情。
- 摇晃：以相同存档和输入过程跑完整10秒，分别覆盖常用数量及高负载数量，记录物品数、柔软分段、接触数和补算步数。
- 结算：覆盖收益浮字、分数滚轮及进入三选一，检查相邻阶段的帧尖峰。
- 冷启动与热启动单独记录；不能将下载时间与稳态帧率混成一个指标。

### 逐项对照

保持其他条件一致，每次仅改变一项：泛光关闭、浮尘关闭、镜头动画关闭；诊断版本再分别旁路通用 Bloom、灯带 Bloom、阴影和样式重复提交。记录改变前后的帧时间分布，不能仅凭“看起来顺滑”确定原因。

使用浏览器 Performance 记录主线程、渲染、GC、长帧与资源请求，并结合引擎内分段计时。若后端没有可用 GPU 时间查询，就保留“渲染方向疑似瓶颈”的结论，不把主线程空闲或总帧时间直接当成 GPU 耗时。

### 建议验收目标

以下为本项目拟定目标，不是现有实测结果：

| 档位 | 目标帧率 | 稳态帧间隔 p95 | 稳态帧间隔 p99 |
|---|---:|---:|---:|
| 桌面及中端手机 | 接近60 FPS | 不超过20ms | 不超过33.3ms |
| 低端设备保底档 | 接近30 FPS | 不超过40ms | 不超过66.7ms |

预热后的完整回合不出现由持续补算引起的连续100ms以上长帧；重复进入三选一、返回主菜单和调整窗口后，RTT与图像句柄数量不持续增长。保留像素边缘、物品原色、冷却灰阶、灯带节奏、点击命中、安全区及跨页旧按下失效行为。

本次同步后69个 Lua 文件通过语法编译。既有纯 Lua 回归返回120个登记案例，其中可选 `cjson` 往返案例因独立 Lua 环境无该库而跳过；其余119个案例通过。这只验证语法与规则层，不代替浏览器性能或真实 Box2D 验收。后续修改物理、时间或成员缓存后，应再次执行对应规则与真实接触测试。
